# 机制说明：Harness² 的两层递归在本演示里如何成立

本文只讲机制与取舍，操作与输出见 README。

## 出发点：开放世界里 RSI 的两个难题

Harness² 论文把递归自我改进（RSI）搬进开放世界时，点出两个难题：

1. **没有真值验证器**：真实任务大多没有标准答案，「改得好不好」无从打分。
2. **改进不泛化**：为单个任务调出的改动，换一个任务往往失效，经验留不下来。

本演示的两个递归层就是对这两个难题的一一回应，场景换成了新闻收集提示词：
驾驭层 = 提示词正文 + 规则开关（只收什么、窗口多大、来源怎么分级、去不去重）。

## 第一层：任务级递归（Propose–Probe–Compose）

一轮改进分三步，全程不使用真值：

- **Propose**：编辑器盯着上一轮产出的**可观察失败**提议修改。失败全部来自产出条目本身的属性——收进来的条目是不是数据盘点（内容类型字段）、是不是三天前的旧闻（距今小时数字段）、同一事件有没有收了三条（事件组字段重复）、来源能不能说清是谁（来源类别与来源名字段）。这些不需要标准答案，数一数就知道。
- **Probe**：每条编辑先单独应用到当前驾驭层，在**同一个任务**上重跑，看指标怎么变。探测版是临时对象，跑完即弃。
- **Compose**：采纳规则只有一条，写在 `contrast/compose.py` 里：**违规总数严格下降，且合规事件收录不下降**。后半句是关键护栏——没有它，系统会发现「什么都不收」是违规最少的策略。本演示中「来源只认官方」违规降到 0 却被拒绝（合规 8 → 4），就是这条护栏在起作用：**靠少收换来的干净，不算改进**。

逐条贪心的顺序也有意义：先采纳的编辑会改变后续编辑的探测基线（例如先开「只收事件」后，窗口编辑面对的违规构成已经不同），对照表里每一行的 before 都是当时的当前版，而不是最初版。

## 第二层：驾驭级递归（改进库）

单期变干净还不够，经验要能过夜。每条被采纳的编辑、以及个别被拒的编辑，会沉淀成一条**教训（Lesson）**写入改进库（JSON 落盘），教训带三样东西：

- **text**：给人看的经验表述；
- **evidence**：产生它的探测证据（哪个指标从几变到几）——没有证据的教训不许进库；
- **effect**：机器可应用的规则改动。被拒编辑的教训 effect 为空（负教训：记录「不要这样做」，供人看，不自动应用）。

新任务的初始驾驭层不是上一期的最终版副本，而是**出厂版 + 逐条应用教训 effect 重建**。区别在于可移植性：教训是脱离了具体任务上下文的规则，下一个完全不同的语料照样能用。本演示里任务二语料全是新条目，带教训起步的初始违规是 1（任务一从零起步是 13），且那 1 个违规（匿名社交来源）是第一期从未出现过的新失败类型——经验迁移覆盖的是「见过的错」，新题型仍要靠任务级递归现场解决，这正是两层递归要同时存在的原因。

## 与论文实现的取舍

| 论文 | 本演示 | 取舍理由 |
|---|---|---|
| 编辑器由 LLM 担任 | 规则编辑器（LLM 仅留接口） | 确定性、可复现、零成本；提议质量不是本演示的主题，对照与拼装才是 |
| 执行器是真实 Agent（OpenCode / Codex） | 规则执行器 | 同上：要演示的是驾驭层如何决定产出 |
| 递归预算 k 可多轮、可并行 | 每期一轮、逐条串行探测 | 一轮已能完整呈现 PPC 闭环与拒绝逻辑 |
| 基准为 JobBench / LAB / WorkBuddy-Bench | 两期构造语料（19 + 14 条） | 构造语料能让每条规则都有独立考题，数字可手工复核 |
| 改进库为持续更新的 improvement harness | 单文件 JSON 教训库 | 可直接打开检视，证据与 effect 一目了然 |
